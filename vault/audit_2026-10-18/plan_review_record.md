## Round 1 (plan v1)
Verdict: **approve_with_changes**

- [major] F1 (P1 (1.3, Row C1)): The annotation plan combines a simulated/assumed-parameter result (PPO 25% on cohort64, simulated, n=20) with a measured real-test result (20/21 real_test day-90 volume with assumed kill rates) in a single ledger entry, alongside a null TTP result, without a required explicit tag distinguishing which figures are simulation-driven (assumed parameters) versus measured. Fix: Split Row C1 annotation into clearly labelled sub-entries: (a) simulated PPO result with 'ASSUMED kill-rate parameter, simulation, n=20, non-confirmatory' tag, (b) real_test day-90 volume result with 'measured outcome, assumed kill rates used in derivation' tag, (c) TTP null stated plainly. Each sub-entry must state explicitly it is not a locked-test confirmatory primary-endpoint result unless it is one.
- [major] F2 (P4): The four threshold settings do not form a crossed sensitivity grid (three vary OFF only at ON=1.0, one varies both jointly) and no interpretation rule for 'robust vs. sensitive' is pre-specified, so any summary judgment drawn from the four points after the fact would itself be an undeclared post hoc interpretation. Fix: Either (a) expand to a minimal crossed grid (e.g., at least 2x2) or (b) explicitly relabel this as a 'corner-point check' rather than a 'sensitivity analysis' in all outputs, and pre-specify in writing, before running, what pattern of counts/means would be described as sensitive versus robust.
- [major] F3 (P3): 'Public metadata only' is not operationally bounded to exclude benchmark/leaderboard/performance-reporting pages, creating risk that outcome information (model performance on a candidate dataset) could leak into the eligibility desk review even unintentionally, which would compromise A13.4's requirement that dataset choice rest on eligibility/logistics only. Fix: Add an explicit exclusion rule to P3: the desk review may consult dataset description pages, licence terms, and cohort/annotation documentation only; it must not open or read any page, table, or section reporting model performance, benchmark results, or leaderboard rankings for any candidate dataset. Any such content encountered incidentally must be noted as excluded-from-review, not used.
- [minor] F4 (P1 (general)): Append-only annotations lack a mandated structured header (date, step ID, nature of entry: measured/assumed/exploratory/correction), risking an auditable vault becoming hard to parse over time even though nothing is deleted. Fix: Require every new ledger annotation to begin with a fixed header: [DATE | STEP-ID | TYPE: measured/assumed/exploratory/correction]. Apply retroactively to all P1 additions in this plan.
- [minor] F5 (P4 / G6): G6 requires the sweep to be 'declared in writing before any run' but the plan does not specify that this declaration is saved as a timestamped artifact prior to execution, so pre-declaration cannot later be verified as genuinely prior rather than reconstructed. Fix: Save the P4 declaration (exact settings, metrics, E_max ratio fixed at 1000) as a timestamped artifact before P4 execution begins, and reference that artifact ID in the P4 output.
- [minor] F6 (P5): No stop condition is defined for the case where re-running the 35-row audit after P1-P4 edits produces a regression (a previously-matching row now fails) as a result of this plan's own edits. Fix: Add a stop condition to P5 (and the Stop conditions section): if any previously-matching audit row fails on re-verification, halt further edits and report to the user before proceeding, analogous to G7.
- [minor] F7 (P1 / H-4 reuse): The plan does not restate that the H-2 and H-3 locked test sets, having been reused as dev data in H-4 step 1 under Amendment 12, are now spent for any future confirmatory purpose; this boundary is assumed but not written into the new ledger entries. Fix: Add a one-line annotation in P1 noting that H-2/H-3 test sets are dev-reused per Amendment 12 and are no longer eligible as locked test sets for any future confirmatory analysis.

Answers to the five review questions:
- q1_study_rules: The plan as written does not relabel nulls or reposition results across endpoint categories, and it explicitly reiterates G1 (no result relabelled, nulls stay null) and G5 (new work labelled exploratory/post hoc). The ledger edits in P1 are annotation-only and append-only, which is the right mechanism. Two real risks remain. First, Row C1 (1.3) mixes a simulated PPO figure (cohort64, n=20, simulated kill rates) with a real-test day-90 volume figure (20/21) in the same annotated entry; unless the annotation visually and textually separates 'simulated/assumed-parameter result' from 'measured result' with the TTP null stated in the same breath, a reader skimming the ledger could conflate an assumption-driven number with a measured locked-test result. The plan says it will state both explicitly, which is correct, but the plan should also require the annotation to state which one is NOT a locked-test confirmatory result. Second, H-4 step 1 already reused the H-2/H-3 locked test sets as dev data post hoc (Amendment 12) before this plan starts; this plan does not re-touch that, which is appropriate, but the ledger entries in 1.1-1.4 should explicitly flag that H-2/H-3 test sets are now spent for confirmatory purposes (they cannot be reused as a future locked test) given their dev reuse. The plan is silent on restating this contamination boundary, which is a gap rather than a violation.
- q2_sweep_design: The P4 design is adequate as an exploratory grid but has avoidable weaknesses. (a) It is asymmetric and sparse: three points vary THRESHOLD_OFF at ON=1.0 (0.50, 0.65, 0.90) and only one point varies ON (0.80, 0.90) jointly with OFF held at default. This is not a real two-way sensitivity grid, it is four ad hoc points, so any claim of 'robust to threshold choice' cannot be supported — only 'these four points behave like X' can be. (b) No replication or variance reporting is specified beyond 'counts and means'; for an adaptive-therapy simulation with stochastic elements (if any stochasticity exists in growth-rate fitting or scheduling) means without spread (e.g., range across the 61 patients, or ties/reversals as done for B1) understate uncertainty — the same tie/reversal reporting used for the E_max grid (7 ties, 0 reversed) should be mandated for every one of the four threshold settings, not left optional. (c) Correctly, no p-values are planned — appropriate for an exploratory grid — but the plan should pre-commit to reporting ALL four settings' full output regardless of outcome (G6 says this) and should state in advance what pattern would be considered 'threshold-sensitive' versus 'robust,' otherwise the post hoc interpretation of the grid itself becomes an unplanned post hoc judgment call. Recommend: declare the interpretation rule before running, and either expand to a full crossed grid or explicitly label this as a 'corner-point check' rather than a sensitivity analysis.
- q3_desk_review: P3 is designed correctly in spirit: public-metadata-only, no labels read, no scoring, explicit statement that A13.4 requires the user's amendment and that dataset choice must rest on eligibility/logistics only. This matches the no-outcome-information-used-to-choose rule. Two gaps should be closed before execution. First, 'public metadata only' needs an explicit operational boundary: it must exclude any paper, leaderboard, benchmark table, or GitHub README that reports model performance on that dataset — the plan should state that the desk review may look at dataset descriptions, licence pages, and cohort/segmentation documentation, but must NOT open any page or section reporting benchmark results, since that would constitute outcome information leaking into dataset choice even if unintentionally. As written 'public metadata' is undefined and could be interpreted broadly enough to include results tables. Second, the yes/no/unknown table needs a rule for what happens to 'unknown' cells — if a criterion (e.g., 'at least 40 patients') can't be confirmed from metadata, the plan should say the cell is marked unknown and NOT inferred or guessed, and that an unknown on any A13.4 criterion blocks selection until the user/amendment resolves it directly with the data provider, not via the assistant downloading anything.
- q4_ledger: Append-only annotation to a vault described as 'the single source for every number in the paper' is acceptable and is in fact the right discipline, provided three things hold, two of which the plan states and one of which it does not. Stated: original text is never deleted (G3), corrections are dated annotations. Not stated: there is no requirement that each new annotation carry a unique dated identifier/version tag and an explicit author/process attribution (e.g., 'automated annotation, 2026-10-18, by this fix-plan step 1.1') so that a future reader can distinguish original measured entries from later desk-review or simulation-derived annotations at a glance without cross-referencing a separate changelog. Without that, 'single source of truth' erodes over time into a palimpsest that's hard to audit even though nothing was deleted. Recommend adding a mandatory annotation header format (date, step ID, nature: measured/assumed/exploratory/correction) to every new ledger entry and annotation in P1.
- q5_missing_or_cut: Missing: (1) No explicit pre-registration timestamp/hash for the P4 sweep declaration itself — G6 says 'declared in writing before any run' but the plan doesn't say the declaration will be saved as an artifact with a timestamp BEFORE P4 executes, which is needed to make the pre-declaration auditable rather than asserted after the fact. (2) No multiplicity accounting across the cumulative set of new comparisons this plan generates (E_max grid already run, now 4 more threshold settings, plus retrain, plus literature check) — the plan correctly avoids p-values for the sweeps, but if any inferential claim (even informal, e.g., 'retrain improved X') is later made comparing retrain vs. original, that comparison is not on the list and no multiplicity control is mentioned for it; the plan should state explicitly that the retrain's within-training-only metrics are descriptive only and not to be used for any confirmatory claim. (3) P5 verification re-runs the 35-row audit but does not say what happens if a row that previously 'matched' now fails because of the P1-P4 edits — there's no explicit rule that a regression in the audit halts further edits (analogous to G7); this should be added as a stop condition. (4) The plan should cut or tighten nothing structurally, but P1.3's combined Row C1 annotation (flagged above) should be split into two clearly separate sub-annotations rather than one merged statement, to reduce the conflation risk between simulated and measured, assumption-driven and measured-driven numbers. (5) No mention of who re-verifies the SHA-256 backups in P0 are actually immutable/stored outside the repo edit path — worth a one-line confirmation step before P1 edits begin.

Go conditions:

New findings:
- [minor] F8: C-B's 'dose-sparing robust' threshold (mean drug % of MTD below 80 in all 8 cells, against a default of 32.4) is extremely loose relative to the observed default value — it would take roughly a 2.5x increase in mean dose fraction before 'robust' could even be challenged. This is stated before results are seen, which satisfies the no-peeking requirement, but the threshold's looseness is not justified against any clinical or operational meaning of 'dose-sparing,' so a 'robust' verdict under this rule would carry little information even though it is procedurally clean. Fix: Either justify why 80% is the meaningful dose-sparing cutoff (e.g. tie it to a clinically or operationally relevant dose-fraction boundary) or tighten it to a value with a stated rationale, and note in the write-up that passing this particular threshold is a weak form of 'robust.'
- [minor] F9: P4's declared interpretation rules (C-A, C-B, C-D) classify 'robust' only via an all-8-cells-must-match-default rule, with no provision for reporting effect sizes or magnitude of deviation when a cell is classified 'sensitive.' The plan says 'naming the cells' but does not commit to reporting by how much each sensitive cell deviates from the default (e.g., magnitude of VR shift, count difference in progression pattern). Fix: Add a requirement that any cell classified as deviating ('sensitive') is reported with the magnitude/direction of deviation from the default cell, not just a binary flag and the cell identity, so a future reader can judge practical significance.
- [minor] F10: P2.2 now updates CLAUDE.md with observed pytest collected/passed/failed counts, but the plan does not say these counts will also receive a dated ledger entry with the R4 header (G3/R4 apply explicitly to vault/PAPER_FINDINGS_LEDGER.md entries); CLAUDE.md is a different file and its update mechanism (overwrite vs. append) is unspecified, risking loss of the history of prior pytest runs. Fix: Specify whether the CLAUDE.md test-count update is append-only or overwrite, and if overwrite, add a corresponding dated ledger entry (with R4 header) recording the before/after counts so the audit trail is preserved outside CLAUDE.md as well.

P4 design comment: The crossed 4x2 design with a pre-registered, binary (all-cells) interpretation rule is methodologically sound for an exploratory, descriptive sweep over an assumed parameter: it avoids the original problem of an unbalanced grid and undeclared post hoc summarization. The handling of the script-44 code-reading finding is a strength — disclosing that ON is expected to be near-inert due to the hard-coded 0.9*peak clause, and keeping it in the design as a falsifiable expectation (C-E) rather than quietly dropping the axis, is exactly the right way to treat a discovered implementation detail: it is written down before running, and any deviation from the expectation will be visible and reported with affected patients. My remaining concerns (F8, F9) are about the informativeness of the thresholds and the granularity of 'sensitive' reporting, not about procedural validity — the no-peeking discipline itself is intact. Reporting raw effect sizes/spread per cell regardless of the robust/sensitive label (as G6 already requires: "all cells are reported; none dropped") partially mitigates F9, but the binary labels could still be over-read as a clean verdict unless deviation magnitudes are foregrounded in the write-up.
